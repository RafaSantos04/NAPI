# API v1: inventário

[← API](README.md) · [Ciclo de vida](../architecture/request-lifecycle.md) · [Autorização](../security/authorization.md)

Fonte: `routes/api.php`, conferido com `php artisan route:list --path=api`
(24 rotas). Todas as rotas abaixo, exceto o login, passam por
`auth:sanctum` e `token.ability` ([ADR-0008](../architecture/decisions/ADR-0008-layered-authorization-model.md)).

**Legenda das respostas:**

| Status | Significado |
|---|---|
| 401 | sem token, token inválido ou expirado, ou dono inativo/excluído |
| 403 `Invalid ability provided.` | o token não tem a ability do método HTTP |
| 404 | sem a permissão funcional (`permission:`), negado em `index`/`show`, ou recurso inexistente |
| 403 | negado por regra contextual da Policy em escrita |
| 409 | a operação violaria uma invariante de domínio (último administrador ativo) |
| 422 | validação |

## Abilities de token

| Método HTTP | Ability exigida |
|---|---|
| `GET`, `HEAD`, `OPTIONS` | `read` |
| `POST`, `PUT`, `PATCH` | `write` |
| `DELETE` | `delete` |

A regra vale para todas as rotas autenticadas, inclusive `/auth/*` e
`/tokens`. A ability limita o token, mas não concede permissão: o IAM do
dono continua valendo.

## Formato das respostas

| Tipo | Formato |
|---|---|
| `index` | `{"data": [...], "meta": {"total", "per_page", "current_page"}}` (15 por página) |
| `show`, `update` | `{"data": {...}}` |
| `store` | `{...}` **sem** envelope `data`, status 201 ([FIND-020](../findings/README.md#find-020--respostas-de-autorização-e-de-tokens-inconsistentes)) |
| `destroy` | `{"message": "..."}` |
| negação funcional ou em `index`/`show` | `{"message": "Not found."}` |
| invariante violada | `{"message": "The system must keep at least one active administrator."}` (409) |

## Autenticação

| Método | Rota | Nome | Ability | Request | Controller | Resposta |
|---|---|---|---|---|---|---|
| POST | `/auth/login` | `auth.login` | — (`throttle:login`) | `Auth\LoginRequest` | `Auth\AuthController@login` | 200 `{user, token}` · 422 · 429 |
| POST | `/auth/logout` | `auth.logout` | `write` | — | `AuthController@logout` | 200; revoga **todos** os tokens |
| GET | `/auth/me` | `auth.me` | `read` | — | `AuthController@me` | 200 `{data: UserResource}` |

- O login emite um token com `read`, `write` e `delete`.
- Auditoria: `login` e `logout` (com `revoked_tokens`).
- Detalhes em [authentication.md](../security/authentication.md).

## Tokens

| Método | Rota | Nome | Ability | Validação | Resposta |
|---|---|---|---|---|---|
| GET | `/tokens` | `tokens.index` | `read` | — | 200 `{data: [{id, name, abilities, created_at, expires_at}]}` |
| POST | `/tokens` | `tokens.store` | `write` | `Auth\TokenStoreRequest`: `name`; `abilities` (`read`/`write`/`delete`, distintas, **subconjunto** das do token atual); `expires_in_days` de 1 a 7 (padrão 7) | 201 `{token, message}` · 403 (abilities maiores que as do token atual) · 422 |
| DELETE | `/tokens/{token}` | `tokens.destroy` | `delete` | `{token}` numérico | 200 · 404 (inexistente ou de outro usuário) |

- Controller: `Auth\TokenController`. Escopo sempre em `$request->user()->tokens()`.
- Auditoria: `token_created` e `token_revoked`.

## Users

Permissão: `users.*` · Policy: `UserPolicy` · Resource: `UserResource`
(`id`, `name`, `email`, `email_verified_at`, `is_active`, `profiles` quando
carregado, timestamps).

| Método | Rota | Nome | Permissão | Policy / onde | Request | Action | Respostas |
|---|---|---|---|---|---|---|---|
| GET | `/users` | `users.index` | `users.view` | `viewAny` / controller | — | — | 200 · 404 |
| POST | `/users` | `users.store` | `users.create` | `create` / FormRequest | `UserStoreRequest` (`name`, `email` único, `password` ≥ 8 `confirmed`) | `CreateUser` | 201 · 422 |
| GET | `/users/{user}` | `users.show` | `users.view` | `view` / controller | — | — | 200 (com `profiles`) · 404 |
| PUT | `/users/{user}` | `users.update` | `users.update` | `update` / FormRequest | `UserUpdateRequest` (`name`, `email`) | `UpdateUser` | 200 · 403 (conta de administrador, para não-admin) · 422 |
| DELETE | `/users/{user}` | `users.destroy` | `users.delete` | `delete` / `$this->authorize` | — | `DeleteUser` | 200 (soft delete) · 403 (a si mesmo, ou administrador para não-admin) · 409 (último admin ativo) |
| PUT | `/users/{user}/profiles` | `users.profiles.update` | `users.update` | `assignProfiles` / FormRequest | `AssignProfileRequest` (`profile_ids` presente, cada um `exists`) | `AssignProfilesToUser` | 200 · 403 (escalação) · 409 (último admin ativo) · 422 |
| POST | `/users/{user}/deactivate` | `users.deactivate` | `users.update` | `deactivate` / `$this->authorize` | — | `DeactivateUser` | 200 `{message, data}` · 403 (a si mesmo, ou administrador para não-admin) · 409 (último admin ativo) |
| POST | `/users/{user}/activate` | `users.activate` | `users.update` | `activate` / `$this->authorize` | — | `ActivateUser` | 200 `{message, data}` · 403 (administrador, para não-admin) |

- Controllers: `UserController`, `UserProfileController`, `UserStatusController` (Fase 4.2). A atribuição de
  perfis **substitui** o conjunto inteiro (`sync`); perfis novos recebem
  `assigned_by` com o ator.
- Autoatendimento (ver a si mesmo) é `GET /auth/me`. `GET /users/{id}` exige
  `users.view` mesmo para o próprio id.
- Status: desativar revoga todos os tokens e remove as sessões web do usuário;
  reativar não devolve nenhum dos dois. Repetir a operação no estado atual não
  altera nada nem audita. `is_active` continua fora de `POST`/`PUT /users`.
- As mesmas Actions atendem a área administrativa (`/admin/users`, [Fase 4.2](../phases/phase-04-2-user-management.md)).
- Auditoria: `user_created`, `user_updated` (nomes dos campos), `user_deleted`, `profile_assigned`, `user_deactivated`, `user_activated`.

## Profiles

Permissão: `profiles.*` (sync: `permissions.update`) · Policy: `ProfilePolicy`
· Resource: `ProfileResource` (`id`, `name`, `slug`, `description`,
`is_system`, `menus` com `key` e `permissions` quando carregado, timestamps).

| Método | Rota | Nome | Permissão | Policy / onde | Request | Action | Respostas |
|---|---|---|---|---|---|---|---|
| GET | `/profiles` | `profiles.index` | `profiles.view` | `viewAny` / controller | — | — | 200 · 404 |
| POST | `/profiles` | `profiles.store` | `profiles.create` | `create` / FormRequest | `ProfileStoreRequest` (`name`, `slug` `alpha_dash`, únicos; `description`) | — | 201 · 422 |
| GET | `/profiles/{profile}` | `profiles.show` | `profiles.view` | `view` / controller | — | — | 200 (com `menus`) · 404 |
| PUT | `/profiles/{profile}` | `profiles.update` | `profiles.update` | `update` / FormRequest | `ProfileUpdateRequest` | — | 200 · 403 (sistema) · 422 |
| DELETE | `/profiles/{profile}` | `profiles.destroy` | `profiles.delete` | `delete` / `$this->authorize` | — | — | 200 · 403 (sistema ou com usuários) |
| PUT | `/profiles/{profile}/menus` | `profiles.menus.update` | `permissions.update` | `syncMenus` / FormRequest | `SyncMenusRequest` (`permissions` presente, até 200 itens, chaves = ids de menus existentes; `can_*` booleanos, as 4 chaves obrigatórias) | `SyncMenuPermissions` | 200 `{message, data}` · 403 (sistema, perfil do próprio ator ou flag que o ator não tem) · 422 |

`is_system` não é aceito na entrada. A sincronização **substitui** toda a
matriz do perfil; `{"permissions": {}}` revoga tudo.

Exemplo de corpo (IDs fictícios):

```json
{
  "permissions": {
    "01J0000000000000000000MENU": {
      "can_view": true, "can_create": false, "can_update": false, "can_delete": false
    }
  }
}
```

## Menus

Permissão: `menus.*` · Policy: `MenuPolicy` · Resource: `MenuResource`
(`id`, `key`, `label`, `route_name`, `icon`, `parent_id`, `order`,
`is_active`, `is_system`, `description`, `children` quando carregado,
timestamps).

| Método | Rota | Nome | Permissão | Policy / onde | Request | Respostas |
|---|---|---|---|---|---|---|
| GET | `/menus/tree` | `menus.tree` | — | — | — | 200 `{data}` sem paginação |
| GET | `/menus` | `menus.index` | `menus.view` | `viewAny` / controller | — | 200 (raízes com 1 nível de filhos) · 404 |
| POST | `/menus` | `menus.store` | `menus.create` | `create` / FormRequest | `MenuStoreRequest` (`key` obrigatória, única, `^[a-z0-9]+(-[a-z0-9]+)*$`; `label`, `route_name` único, `parent_id` `exists`…) | 201 · 422 |
| GET | `/menus/{menu}` | `menus.show` | `menus.view` | `view` / controller | — | 200 (com `children`) · 404 |
| PUT | `/menus/{menu}` | `menus.update` | `menus.update` | `update` / FormRequest | `MenuUpdateRequest` (`key` **proibida**) | 200 · 422 |
| DELETE | `/menus/{menu}` | `menus.destroy` | `menus.delete` | `delete` / `$this->authorize` | — | 200 · 403 (de sistema ou com filhos) |

- `key` é o identificador de permissão (`{key}.{ação}`). `route_name`,
  `label` e `is_active` são só navegação: alterá-los **não** muda a
  autorização.
- `/menus/tree` devolve, para **qualquer usuário autenticado**, os menus
  ativos em que ele tem `{key}.view`, em árvore de profundidade arbitrária.
  Um filho só aparece com o pai visível. A árvore não concede acesso.
- `/menus/tree` é registrada antes de `/menus/{menu}`; veja
  [request-lifecycle.md](../architecture/request-lifecycle.md#ordem-de-rotas).

## Fora da API

- `GET /up`: health check do Laravel (`bootstrap/app.php`).
- O menu `audit-logs` existe no seed, mas **não há endpoint** de auditoria.
